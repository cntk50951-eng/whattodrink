# EPIC F — 组局（Group Gathering）产品设计 v0.1

> 生产线 F 新开，主力承载“组局”新功能。本文为产品设计草案，待评审后拆为 F.1~F.n 写入 `PRODUCT_BACKLOG.md`。
> 状态：Draft / 待评审 | 作者：Muse + Chris | 日期：2026-09-27

---

## 1. 背景与定位

### 1.1 为什么做组局
- 现有 App 已验证：选酒→想喝足迹→地图发现→乾杯/在线约酒（浅社交），但**从线上兴趣到线下真实见面仍断层**。
- 香港 25–35 岁都市年轻人：社交圈固化、跨区/跨行业认识新朋友机会少；“喝一杯”是最低门槛的社交货币。
- 组局 = **以酒为媒介的可控陌生人/半熟人线下小聚**，不是约会App、不是活动票务，是“每人带一支酒的品酒会”为原型的主题化组局引擎。

### 1.2 与现有 EPIC 的关系
- EPIC 1.0（地图基建）→ 组局在地图上做发现层（新图层，不污染他人打卡层）
- EPIC 3.0（社交）→ 复用好友/乾杯/在线态，作为信任加成与二度人脉
- EPIC 4.0（内容/墙）→ 复用照片/点赞/检举能力
- **不做**：电商卖酒、酒吧预订系统、IM 重做（复用 D 线聊天）

### 1.3 一句话价值主张
> “带一支你想分享的酒，来认识 6 个同城的人——地点你定，主题你选，AA 各付各的，平台只做撮合。”

## 2. 受众人群（B+C 混合）

基于你的选择 B（主题开放）+ C（熟人裂变为基座），F 线同时服务两类动因，共享同一引擎：

| 人群 | 占比* | 核心JTBD | 典型画像 | 对应组局形态 |
|---|---|---|---|---|
| **A. 社交拓展者** | 40% | 认识新朋友、扩大圈子 | 26岁，刚搬到将军澳，朋友都在港岛，想周末认识同好 | 开放主题：BYOB品酒会 / 酒吧探店 / CityWalk配酒 |
| **B. 轻尝鲜者** | 30% | 想试酒但不懂，想有人带 | 29岁，平时只喝 Asahi，想试清酒但怕踩雷 | 跟局：有人带酒、有人讲解，低门槛 |
| **C. 资深饮家/主理人** | 15% | 分享/组局有成就感 | 33岁，藏酒多，乐意带 Yamazaki 做小分享会 | 发局：当 host，主题品酒（单一麦芽/自然酒） |
| **D. 熟人小聚发起人** | 15% | 把线上好友落到线下 | 已有 3 个乾杯好友，想约一次烧烤配酒 | 半闭局：仅好友/二度可见，可一键邀约 |

*占比为 MVP 阶段预估，用于优先级。

**共同特征**：香港、18–35、已过年龄闸门、愿意为线下社交付出 2–3 小时、对“公开场合见陌生人”接受度中等（需安全设计托底）。

**非目标（初期不服务）**：
- 未成年（<18 强制拦截）
- 以醉酒/拼酒为目的的人群（文案与规则明确排除）
- 需要私密空间的大型商务宴请

## 3. 风险与合规（对应你的“公开场合先行 + 免责撮合”）

### 3.1 风险矩阵

| 风险类 | 具体场景 | 概率* | 影响 | MVP 缓解 | 后期增强 |
|---|---|---|---|---|---|
| **人身安全** | 陌生人线下骚扰/尾随 | 中 | 高 | ①强制公开场所 ②人数上限 ③一键检举/拉黑 ④组局页显人数与历史评价 | 实名/手机验证、合作场地驻场、紧急联系人 |
| **酒精风险** | 过量饮酒、未成年饮酒 | 中 | 高 | 年龄闸门 18+、文案“理性饮酒”常驻、人数≤8、时长≤3h、禁止拼酒主题 | 合作场地持牌、限量提醒、呼叫代驾入口 |
| **法律/免责** | 平台被认定为活动组织者 | 中 | 高 | **免责申明（见 3.2）**：平台仅信息撮合，不指定场地、不代收费用、不承担线下履约 | 合作场地认证体系 + 保险 |
| **隐私/doxxing** | 位置+照片+社交图谱泄露 | 中 | 高 | 位置模糊到 200m 内不显示精确门牌、照片可选、陌生人不可私信（仅组局内申请） | 场地认证后精确度提升需二次同意 |
| **运营风险** | 放鸽子、幽灵局、刷局 | 高 | 中 | 报名需点“确认参与”、Host 可批/拒、签到二维码、信用分 | 保证金/押金（后期） |
| **内容风险** | 垃圾/广告局 | 中 | 中 | 标题/描述敏感词、举报、Host 历史局公开 | 人工复审 |

### 3.2 免责申明（MVP 文案草案，需法务复核）
> **组局免责声明（用户发布/报名时二次确认）**
> 1. 本平台仅提供组局信息发布与撮合，不组织、不指定、不参与线下活动。
> 2. 线下地点由发起人自行选择并注明，建议选择持牌公开餐饮场所；参与者自行评估场地安全性并 AA 自行结算，平台不代收费用。
> 3. 参与者需已年满 18 岁，理性饮酒，遵守香港法例与场地规定。
> 4. 如遇骚扰/不适，请立即离开并使用“检举/紧急求助”入口。

此声明在**发布页底部 + 报名确认弹窗**双处出现，需勾选才能提交。

### 3.3 场合演进（呼应你的分期）
- **Stage 1（MVP，免责撮合）**：不指定场地，用户自填“公开场所建议”（文案引导：如“中环 Soho 持牌餐吧 / 尖沙咀海旁日间野餐区”），平台提供**建议清单**（静态列表，非绑定），不做地理围栏强制。提交时校验：禁止填住宅/私宅/酒店房间关键词。
- **Stage 2（认证合作场地）**：引入 `venues` 库，场地持牌验证、人流/监控、合作折扣；组局可“关联认证场地”获蓝 V 徽章与流量加权；用户仍可自填，但认证局在发现页优先。

## 4. 组局核心定义（B+C 落地）

### 4.1 组局 = 主题化小聚引擎，品酒会是首发主题
- **主题（Theme）**：初期 6 类（可扩展）
  - 🍶 BYOB品酒会（每人带一支，默认主题）
  - 🍢 烤肉配酒
  - 🏙️ 微醺 CityWalk
  - 🍸 酒吧探店
  - 🎲 酒桌游戏夜
  - 🧊 无酒精/低酒精友好局（照顾不饮酒者）
- **地点（Place）**：用户自填文本 + 可选坐标（地图选点，模糊显示）；关联认证场地可选。
- **人（People）**：Host 1 人 + 参与者 2–8 人（MVP 上限 8，含 Host），支持“仅好友可见/公开”两种可见性。
- **物（Bring）**：BYOB 主题下，每人带酒字段为必填（酒名/类型）；其他主题为选填。

### 4.2 角色与权限
- **Host（发起人）**：创建、编辑、审批申请、取消、发起签到码。
- **Applicant（申请人）**：申请加入（附一句话+带的酒）、等待审批、取消申请。
- **Participant（已确认）**：签到、评价、检举。
- **Viewer（围观）**：可看详情、不可看精确地点（确认后可见）。

### 4.3 可见性（满足 C 的熟人基座）
- `visibility`: `public`（全员地图/列表可见） / `friends`（仅好友+二度可见，复用 `friends` 表） / `invite_only`（仅链接/邀请可见，MVP 可先不做）
- 好友加成：若组局中有你的好友，已在列表卡上显示“有 2 位好友参与”。

## 5. MVP 闭环流程（你选的 A）

```
发布 → 发现 → 申请 → 审批 → 行前提醒 → 签到 → 互评 → 归档
```

### 5.1 状态机
`draft` → `open`（招募中） → `full`（满员） → `ongoing`（到点） → `checked`（签到态） → `completed` → `archived`
分支：`cancelled`（Host 取消，需说明原因，通知已确认者）、`expired`（过期未满员自动归档）

### 5.2 关键页面/交互（v2 风格，沿用现有 design system）

**1. 发布页（/v2/gatherings/new）**
- 必填：标题（≤30字）、主题（6 选1）、时间（未来 2h–14 天）、人数（2–8）、地点文本+地图选点（模糊）、带的酒（BYOB 必填）、简介（≤200字，引导理性饮酒文案）、免责勾选
- 选填：可见性、是否需审批（默认需 Host 审批）、费用说明（AA 文本，非支付）

**2. 发现**
- 入口：v2 地图新增“组局”图层开关 + 底部列表 Tab
- 地图：组局 pin（区别于打卡 pin，用“人+酒杯”图标，色板用现有 accent 延伸）
- 列表：卡片含 主题徽章、时间、地点区（如“中环”）、人数进度 3/6、好友加成、认证场地蓝V
- 筛选：距离、时间、主题、仅看好友参与的局

**3. 详情页（/v2/gatherings/[id]）**
- 首屏：标题+主题+时间+地点（模糊/精确按状态）、人数进度、Host 头像/性别/历史局评分
- 中段：简介、带的酒清单（已确认者）、地点建议与免责提示
- 底栏：申请加入（附言+带的酒）/ 等待审批中 / 已确认（显示精确地点与签到入口）/ 已满员
- 次级：参与者头像墙、评价区、检举入口

**4. Host 管理**
- 申请列表：申请人卡（头像/性别/历史履约率/带的酒/附言）→ 通过/拒绝（一键）
- 一键分享链接（复用 invite_only 预留）

**5. 签到（到点前 30min 开放）**
- Host 展示二维码（每 30s 刷新，防截屏复用）
- 参与者扫码签到（或 Host 手动勾选），签到后地点精确化、开启评价

**6. 互评（签到后 48h 内）**
- 1–5 星 + 标签（准时/友善/分享欲强） + 可选文字；匿名聚合，不显示单人给分
- Host 与参与者互评，履约率 = 签到/确认数，影响后续推荐权重

### 5.3 通知
- 申请、通过/拒绝、满员、开始前 24h/2h 提醒、取消、签到开放、评价邀请（复用现有 realtime/推送基建，先用站内 Bell）

## 6. 数据模型（MVP，最小可用）

```sql
-- 组局主表
gatherings (
  id uuid pk,
  host_id uuid fk users,
  title text, -- 30
  theme text check in ('byob','bbq','citywalk','barhop','game','soft'),
  description text, -- 200
  location_text text, -- 用户自填
  lat double, lng double, -- 模糊坐标，精确仅确认后可见
  venue_id uuid nullable fk venues, -- 关联认证场地（Stage2）
  starts_at timestamptz,
  ends_at timestamptz, -- 3h 默认
  capacity smallint check 2..8,
  visibility text check in ('public','friends'),
  approval_mode text check in ('manual','auto'), -- MVP 默认 manual
  bring_text text, -- 带的酒/备注
  status text,
  created_at, updated_at
)

gathering_members (
  gathering_id fk,
  user_id fk,
  role text check in ('host','participant'),
  bring_text text,
  joined_at,
  checked_in_at nullable,
  primary key (gathering_id, user_id)
)

gathering_applications (
  id uuid pk,
  gathering_id fk,
  user_id fk,
  message text, -- 申请附言
  bring_text text,
  status text check in ('pending','approved','rejected','cancelled'),
  created_at
)

gathering_reviews (
  id uuid pk,
  gathering_id fk,
  reviewer_id fk,
  reviewee_id fk,
  rating smallint 1..5,
  tags text[],
  body text nullable,
  created_at,
  unique (gathering_id, reviewer_id, reviewee_id)
)

venues (Stage2)
  id, name, address, lat,lng, license_no, verified boolean, badge text

-- 衍生：信用分可由 reviews + checkin 率计算，不单独表
```

**与现有表复用**：`users`（头像/性别/mode）、`friendships`（可见性与好友加成）、`checkins`（可选：组局签到后自动生成一条“组局足迹”打卡，复用足迹地图）

**PDPO 要点**：位置仅存模糊坐标，精确仅在确认参与后对参与者可见；申请附言/评价内容需可删除。

## 7. 信任与风控细节

- **人数/时间硬约束**：2–8 人、时长 ≤3h、未来 2h 后才可发布（防即时约）
- **关键词拦截**：地点/标题含“私宅/酒店/住宅/上楼”等 → 提示改为公开场所
- **频控**：每人每周最多发 2 局、同时进行中 ≤1 局（防刷）
- **检举**：组局卡常驻旗标，类别：骚扰/虚假信息/未成年/其他，触发后人工复审，命中则下架+信用扣分
- **黑名单**：拉黑后对方局不再出现在你的发现页
- **年龄**：发布/报名前二次校验 `users.dob` ≥18，未填则拦截

## 8. 度量（MVP 是否成立）

| 阶段 | 指标 | 目标（首月，50 种子用户） |
|---|---|---|
| 供给 | 周新增组局数 | ≥10 |
| 需求 | 申请率（浏览→申请） | ≥15% |
| 撮合 | 审批通过率 | ≥60% |
| 履约 | 签到率（确认→签到） | ≥70% |
| 体验 | 互评率 / 平均分 | ≥50% / ≥4.2 |
| 安全 | 检举率 | <2% |

若签到率 <50% 或检举 >5%，暂停放量，先修信任。

## 10. 待确认（Decision Log）

1. **地图图层 vs 独立 Tab**：组局是否与打卡同图层？建议独立图层开关，避免打卡层过载（需设计评审）。
2. **费用**：MVP 是否完全不碰钱（纯 AA 文本）？建议是，支付留到 F.4 再议。
3. **主题扩展**：首批 6 主题是否足够？BYOB 是否强制带酒字段？
4. **审核策略**：默认 manual 还是 auto？建议 manual（Host 有掌控感，安全更高）。
5. **二度人脉**：friends 可见是否含二度？建议 MVP 仅一度，复杂度低。
