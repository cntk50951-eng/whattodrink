## 0. 版本說明

本版為重構版，取代先前草案的 EPIC 2.0／3.0。核心策略轉折：AI 推薦（EPIC 2.0）是使用者「決策時刻」的入口，不是護城河本身；足跡、社交、地圖（EPIC 3.0）才是通用 AI 應用結構上做不到、真正建立壁壘的部分。兩者透過「推薦結果自動生成足跡」這條線緊密相連，而非各自獨立的功能。本地內容策展與多人酒桌遊戲列入 EPIC 4.0，暫緩開發，待核心驗證後再規劃。

## 1. 產品願景

大部分人都有「喝一杯」的習慣——無論是一人獨酌還是朋友小聚，無論心情悲喜，生活中總少不了那一杯酒的陪伴。

想像加班後的一個雨夜，外面下著雨，身心俱疲的你很想喝一杯，卻在啤酒、紅酒、威士忌與果酒之間猶豫不決——每一種都想嘗試，卻懶得花心思選擇，那就讓天意來決定今晚喝什麼。喝下這杯酒時，你還能記錄下此刻的心情。

再想像你走進便利店，面對滿櫃的酒款無從下手——用我們的系統，只需拍一張照片，就能自動幫你挑選合適的酒。

又或者，在一個悠閒的假日午後，你決定晚上吃烤肉，卻不知該配什麼酒——那就讓系統根據你的食物與心情，為你推薦最適合的一款。

與朋友聚會時，這款產品還能支援多人線上酒桌遊戲，讓互動與氣氛瞬間拉滿。

我們系統的核心，是一套基於個人情緒、偏好等數據，結合 AI 分析的決策引擎，能精準掌握用戶當下的狀態，做出最佳推薦。

讓選酒成為一種驚喜，讓選酒成為一種樂趣，讓飲酒的過程充滿歡聲笑語——不必糾結今晚喝什麼，只需享受這個過程。

最終，我們希望打造一個分享型社區：把飲酒時的心情記錄下來、分享出去；同時挖掘並推薦更多優質的香港本地酒吧，成為一個優質的流量入口。

**我們要做什麼**
- 優質而多元的飲酒、生活內容平台
- 優質的數據護城河
- 優秀的流量入口

**不做什麼**
- 不做專業酒類品鑑——這是一個紮根生活的平台，讓選酒飲酒成為每個普通人的樂趣
- 不做電商、零售、比價平台，不直接賣酒

## 2. 目標用戶與核心場景

**Persona**：25–35 歲香港都市年輕人，涵蓋社交型飲酒、朋友聚會、家庭小酌等場景。

**核心使用場景**：
1. 「今晚喝什麼」——獨自一人或臨時聚會，不知道該喝什麼
2. 拍照推薦——拍貨架讓 AI 讀出實際可買到的酒款，或拍自己／食物／環境讓 AI 讀場合氛圍給建議
3. 用文字描述心情、場合、食物搭配，取得推薦
4. 取得推薦後自動累積「想喝」足跡，可回顧、可分享
5. 在地圖上發現其他人的公開足跡，互相乾杯、建立好友
6. 朋友聚會、破冰時的助興酒桌遊戲（EPIC 4.0，暫緩）

## 3. 合規與法律考量（香港）

以下為產品規劃參考，非正式法律意見，正式上線前應諮詢香港執業律師確認最新規定。

- **法定年齡**：香港法定飲酒／購酒年齡為 18 歲（《應課稅品（修訂）條例》2018）。本產品不販售酒類，零售相關條文不直接適用，但作為酒精相關內容平台，建議設置年齡確認閘門，符合廣播守則「酒類內容僅針對成年受眾」的審慎原則
- **PDPO 六項保障原則**：自拍照、位置、聊天內容的收集需明確目的並取得同意（收集原則）；不可挪作未經同意的其他用途，例如轉售第三方（使用限制原則）；使用者需能查閱、更正、刪除自己的資料（查閱權——本產品的足跡刪除、好友刪除設計已符合此原則）
- **2021 年反起底（doxxing）修訂**：定位＋照片＋社交圖譜同時存在時，若資料被用於騷擾或起底他人屬刑事罪。這是「陌生人僅能發乾杯邀請、不可私訊、需頻率限制與封鎖檢舉機制」這個設計方向的直接依據，非加分項
- **跨境資料傳輸**：若 AI 分析呼叫海外雲端服務，需向使用者揭露資料可能傳輸至境外處理並取得同意
- **酒類廣告守則**：對外行銷素材不可將酒精包裝成獎品／贈品呈現；產品內部的隨機推薦機制本身不受此限，但對外行銷文案用詞需留意

## 4. EPIC

### EPIC 1.0　UI & Prototype

**UR 1.0**
作為用戶，我希望無論在筆電或手機瀏覽器上，都能看到可自適應螢幕大小的網頁，這樣切換設備時，不會因螢幕尺寸不同而影響視覺體驗。

**UR 1.1　首頁互動式 Bento Grid 框架**

作為（匿名或已登入的）用戶，我希望打開首頁就能以卡片形式看到產品的核心使用場景，並且能直接點擊卡片體驗，這樣我不需要先註冊、也不需要等待輪播，就能立刻理解並試用這個產品。

*版面規則*
- 採用 Bento Grid（非對稱卡片網格），不使用 carousel／輪播元件
- 首頁展示 3 個 demo 卡片，非等權重：
  - 主卡片（視覺權重最大）：隨機抽一杯
  - 次卡片 ×2：拍照推薦、文字描述推薦
- 響應式規則：桌面多欄不對稱排列；平板收攏為 2 欄；手機收攏為單欄堆疊，用戶自然向下滑動瀏覽，不自動輪播

*卡片入口交互*
- 主卡片（隨機抽一杯）：點擊後原地展開，直接顯示互動結果，匿名即可使用、無需登入
- 次卡片（拍照推薦／文字描述推薦）：點擊後跳轉至該功能的專注頁面，因涉及相機權限／輸入欄位，不適合原地展開

*主題與樣式*
- 所有卡片的顏色、邊框、hover／active 狀態，必須透過主題 token 讀取，不可寫死顏色值，確保用戶切換主題時卡片即時跟隨變化

*多語言*
- 卡片標題、說明文字需支援 i18n key，架構需可擴展，不綁死語言數量（現階段依 UR1.5 暫不啟用多語言，見下）

*無障礙*
- 尊重 `prefers-reduced-motion`：用戶關閉動態效果時，卡片展開改為無動畫的直接切換
- 每張卡片 DOM 順序須與視覺呈現順序一致
- 所有主題下，卡片文字與背景對比須符合 WCAG AA（一般文字 4.5:1／大字 3:1）

*邊界情況／失敗處理（僅限首頁框架本身）*
- 主卡片互動時，若網路不穩導致結果無法即時返回，需有 loading 狀態與逾時提示
- 次卡片點擊跳轉時，若目標頁面載入失敗，需有明確的錯誤提示並可返回首頁

*範圍說明*
- 拍照推薦、文字描述推薦這兩個次卡片，UR1.1 只負責「點擊後正確跳轉到對應功能頁」；相機權限等交互細節屬於各自功能頁的 UR

*驗收標準（Acceptance Criteria）*
- AC1：三個 demo 卡片以 Bento Grid 呈現，非等權重版面
- AC2：桌面／平板／手機三種斷點下，版面可正確響應式收攏，不使用輪播元件
- AC3：主卡片可匿名點擊、原地展開、產生真實隨機結果
- AC4：次卡片點擊後可正確跳轉至對應功能頁
- AC5：切換主題時，所有卡片樣式即時同步更新
- AC6：`prefers-reduced-motion` 開啟時，動畫效果被移除
- AC7：所有主題下，卡片對比度通過 WCAG AA 自動化檢測

**UR 1.2　語言與主題切換元件**

作為（匿名或已登入的）用戶，我希望語言和主題的切換方式更直覺、更符合年輕族群的使用習慣，而不是傳統的下拉選單。

*語言切換*
- 桌面／手機皆採用常駐分段式按鈕（segmented control）
- 初期支援：繁體中文、簡體中文、English；超過 4 個語言時降級為「更多」清單

*主題切換*
- 桌面：頁首主題按鈕點擊後，以 anchored popover 彈出視覺化色卡選單
- 手機：改以 bottom sheet 從底部滑出
- 色卡選單每個主題需顯示視覺縮圖，選中狀態需有明確標示
- 色卡視覺語言需與首頁 Bento Grid 卡片一致

*主題與樣式*
- 語言／主題切換元件本身的樣式也需讀取主題 token

*無障礙*
- 分段式語言按鈕支援鍵盤左右鍵切換
- 色卡選單開啟時焦點自動移入，關閉後焦點返回觸發按鈕
- Bottom sheet 支援手勢、背景點擊、關閉按鈕三種關閉方式

*邊界情況／失敗處理*
- 語言／主題選擇即時生效並記住使用者選擇
- 主題 token 讀取失敗時自動 fallback 至 Nova 預設主題

*驗收標準（Acceptance Criteria）*
- AC1：語言切換為常駐分段式按鈕，不使用下拉選單
- AC2：語言選項超過 4 個時降級為清單
- AC3：主題切換桌面用 popover、手機用 bottom sheet
- AC4：色卡選單有視覺縮圖並清楚標示選中主題
- AC5：語言／主題切換元件樣式隨主題 token 即時更新
- AC6：分段按鈕支援鍵盤操作
- AC7：Bottom sheet 支援三種關閉方式
- AC8：語言／主題選擇被記住
- AC9：主題設定載入失敗時自動 fallback

**UR 1.3　主題系統技術 POC（Phase 1，UI style 目錄）** ／ **UR 1.4　主題系統技術 POC（Phase 2，Stitch）**

（內容同前版：各風格產出獨立 HTML demo，含開獎動畫樣本、渲染家族分類與長期製作成本評估，非即時切換 demo；已完成 review，選定 Hand-drawn Doodle 風格，見 UR1.5）

### EPIC 2.0　推薦入口

**UR 2.0　年齡確認閘門**

作為平台方，我需要在使用者第一次進入酒類相關內容前，確認使用者已滿 18 歲，符合香港對酒精相關內容的審慎原則（見第 3 節合規考量）。

*範圍*
- 首次使用（匿名或登入）觸發任何酒類推薦流程前，需完成一次性年齡確認
- 確認結果持久化保存：登入用戶綁定帳號，匿名用戶綁定裝置本地儲存
- 未滿 18 歲者不得繼續使用酒類推薦／展示功能，需顯示明確說明

*不在範圍內*
- 不做嚴格身分證件驗證，此為內容審慎閘門，非零售場景的法定年齡查核義務

*驗收標準（Acceptance Criteria）*
- AC1：首次使用前必須完成年齡確認才能進入推薦功能
- AC2：確認結果持久化，不重複詢問
- AC3：未滿 18 歲者無法繼續使用酒類相關功能

**UR 2.1　拍照喚起與權限處理**

作為（匿名或已登入的）用戶，我希望點擊拍照推薦次卡片後能直接拍照，鏡頭可以拍貨架，也可以拍自己、食物、環境，不限定拍攝對象，AI 會依照片內容自動判斷情境。

*範圍*
- web 環境需請求相機權限（`getUserMedia`／`<input capture>`），拒絕後提供上傳照片的替代方案
- 首次請求前需簡短說明用途；首次使用需明確告知資料使用方式並取得同意（呼應 PDPO 收集原則）
- 不限定拍攝對象，鏡頭可拍攝任何內容，交由 UR2.4／UR2.5 判斷情境類型

*邊界情況／失敗處理*
- 無相機裝置：直接導向上傳照片
- 永久拒絕權限：提供操作指引

*驗收標準（Acceptance Criteria）*
- AC1：點擊次卡片後正確喚起相機或請求權限
- AC2：拒絕權限後可透過上傳檔案繼續完成流程
- AC3：首次使用需顯示資料使用同意提示並取得明確同意
- AC4：無相機裝置時自動導向上傳照片路徑

**UR 2.2　拍照後的輸入補充頁面**

作為用戶，我希望拍完照片後，能看到照片預覽，並且可以選擇補充文字或語音說明我的需求，也可以直接跳過送出。

*範圍*
- 顯示照片預覽，提供「重新拍攝」入口
- 提供文字輸入框與錄音按鈕，兩者選填，皆未填寫時仍可直接送出

*無障礙*
- 錄音按鈕需有清楚的錄音中狀態視覺與文字標示，支援鍵盤操作

*驗收標準（Acceptance Criteria）*
- AC1：拍照／上傳完成後正確顯示照片預覽
- AC2：送出前可重新拍攝
- AC3：文字與語音輸入皆為選填，皆未填寫時仍可送出
- AC4：錄音中狀態有清楚的視覺與文字提示

**UR 2.3　語音轉文字管線**

作為用戶，我希望用語音描述我的心情或需求時，系統能準確轉成文字。

*範圍*
- 錄音完成後呼叫 STT 服務，轉換結果顯示給用戶確認／編輯後才送出
- 初期支援語言：粵語、普通話、英語

*邊界情況／失敗處理*
- 轉錄失敗：提示重新錄音或改用文字輸入
- 錄音時長設上限，超過自動停止並提示

*驗收標準（Acceptance Criteria）*
- AC1：錄音完成後可正確轉換為文字並顯示確認
- AC2：用戶可在送出前編輯轉錄文字
- AC3：轉錄失敗時提供重新錄音或改用文字的路徑
- AC4：錄音超過時長上限自動停止並提示

**UR 2.4　AI 分析與結果呈現**

作為用戶，我希望不管拍的是貨架還是自己和食物，AI 都能給我最多 3 款推薦，並且推薦結果會自動在我目前的位置生成一筆「想喝」足跡，這樣我不需要另外操作就能開始累積我的足跡。

*範圍*
- 統一處理三種輸入情境（文字／語音轉文字／無輸入），最終以「圖片＋文字（可能為空）」送給 AI 分析
- AI 需先判斷照片屬於「貨架情境」或「人物／場景情境」，套用 UR2.5 對應規則
- 送出後顯示符合品牌動效調性的 loading 狀態（沿用 UR1.5 的動效 token）
- 分析成功後，除顯示推薦結果，同時在使用者當前定位（街區／場館級模糊定位）自動生成一筆「想喝」足跡（對應 UR3.1），預設僅自己可見

*不在範圍內*
- 情緒／表情辨識：不對人物照片做臉部表情分析，只讀取環境／場景線索，避免不必要的敏感生物特徵資料處理

*邊界情況／失敗處理*
- AI 回傳「無法辨識」：顯示對應提示並提供重新拍攝入口
- 網路異常或逾時：顯示提示並提供重試選項

*驗收標準（Acceptance Criteria）*
- AC1：三種輸入情境皆能正確送出圖片與文字給 AI 分析
- AC2：分析過程顯示符合品牌動效調性的 loading 狀態
- AC3：分析成功時正確顯示最多 3 款推薦酒款與理由
- AC4：AI 回傳無法辨識時顯示對應提示並提供重新拍攝入口
- AC5：網路異常或逾時時顯示提示並提供重試選項
- AC6：分析成功後自動生成對應的「想喝」足跡，預設可見性為僅自己
- AC7：人物照片的分析不涉及臉部表情辨識，僅讀取環境線索

**UR 2.5　AI 系統提示詞設計（雙模式）**

作為產品經理，我需要一份定義清楚的系統提示詞，能區分「貨架」與「人物／場景」兩種情境並套用對應規則，確保輸出格式穩定、可被前端可靠解析。

*設計原則*
- 第一步先判斷照片情境：貨架（shelf）或人物／場景（scene）
- 貨架情境：僅能推薦照片中標籤清楚可辨識的真實品牌，嚴禁編造；不足 3 款可回傳較少；無輸入時採類別多樣性優先
- 人物／場景情境：不要求品項出現在照片中（喝的酒通常不在畫面裡），改依環境線索（食物類型、場合、光線）與使用者輸入，推薦常見易購得的酒類；不做臉部表情／情緒辨識；無輸入時依場景氛圍做合理推測，理由需說明是根據場景推測，不宣稱讀懂使用者心情
- 兩種情境皆最多推薦 3 款，皆為結構化 JSON 輸出

*草稿版本*
```
你是「WhatToDrink」的選酒助手，個性像一個懂酒但不擺架子、很會看場合的朋友，
不是專業侍酒師，語氣輕鬆、簡短、有梗，符合香港25-35歲年輕族群的說話方式。

【第一步：判斷情境】
先判斷照片屬於：
- "shelf"：貨架、酒櫃、瓶身特寫等，畫面中有實際酒類商品
- "scene"：人物、食物、場合、環境等，畫面中不是酒類商品特寫

【貨架情境 (shelf)】
1. 辨識照片中實際可見、且清楚可辨識品項的酒類選項
2. 從中挑選最多3款推薦，每款附一句話理由（40字以內，輕鬆有畫面感，
   不用專業品鑑術語）
3. 只能報出標籤清楚可辨識的實際品牌名稱，嚴禁編造。
   若某瓶因角度／反光／遮擋無法確定品牌，優先選其他清楚可辨識的品項；
   若清楚可辨識品項不足3款，只回傳實際能辨識到的數量，不可湊數編造
4. 若使用者有文字／語音輸入，以其描述為主要依據挑選3款
5. 若使用者沒有輸入，採「類別多樣性優先」：挑選跨越不同酒類的3款；
   若貨架類別本身單一，仍以真實可辨識品項為準，不犧牲真實性換取多樣性

【人物／場景情境 (scene)】
1. 根據畫面中的食物、場合、光線、氛圍等環境線索，
   以及使用者提供的文字／語音（若有），推薦最多3款常見、容易買到的酒類
   （可以是類型如「氣泡酒」，也可以是常見品牌）
2. 不要求該酒款出現在照片中
3. 絕不對人物的臉部表情或情緒做判讀，僅根據環境線索與使用者文字描述
4. 若使用者有輸入，以其描述為主要依據
5. 若使用者沒有輸入，依場景氛圍做合理推測（例如戶外烤肉場景→
   啤酒／氣泡酒／淡口味調酒），理由需說明是根據場景推測，
   不宣稱讀懂使用者心情

【無法辨識照片內容時】
若照片模糊、無法判斷情境，或看不出任何酒類／場景相關內容，
不要編造答案，回傳明確的「無法辨識」狀態，並給友善提示
（例如「這張照片看不太清楚，要不要再拍一次？」）。

【輸出格式】
請以下方JSON格式回傳，不要輸出JSON以外的文字：
{
  "status": "success" | "no_alcohol_detected" | "unclear_image",
  "mode": "shelf" | "scene",
  "recommendations": [
    { "drink_name": "品項名稱或類型", "reason": "一句話推薦理由（40字以內）" }
  ],
  "message": "當status不是success時，給使用者看的友善提示文字"
}
說明：recommendations陣列最多3項；貨架情境若清楚可辨識品項不足3款，
陣列長度可以少於3，但不可為了湊數而編造不存在的品項。
```

*驗收標準（Acceptance Criteria）*
- AC1：提示詞能正確區分貨架／人物場景兩種情境並套用對應規則
- AC2：貨架情境維持嚴禁編造品牌名稱的規則
- AC3：人物／場景情境明確不做臉部表情／情緒辨識
- AC4：輸出格式含 mode 欄位，供前端與 UR3.1 足跡記錄使用
- AC5：語氣符合品牌調性，經 PM review 確認不帶專業品鑑腔調

### EPIC 3.0　足跡與社交地圖（差異化壁壘）

*定位*
- 通用 AI 應用是單人、非空間、非即時的；本 EPIC 做空間＋社交＋即時的事，這是通用 AI 聊天在結構上做不到的維度
- 與產品願景「分享型社區／流量入口」直接呼應，也是 EPIC 2.0 推薦結果的自然去處：決策→足跡→社交→回饋給推薦引擎

**UR 3.1　自動生成「想喝」足跡＋編輯／刪除**

作為使用者，我希望每次獲得 AI 推薦後，系統自動在我目前位置生成一筆「想喝」足跡，我可以編輯它、加上動態心情，也可以刪除它。

*範圍*
- 觸發時機：UR2.4 分析成功時自動生成，不需使用者額外操作
- 定位：街區／場館級模糊定位，不存精確座標
- 預設可見性：僅自己可見
- 可編輯足跡內容（補充心情文字、更換配圖），可完全刪除
- 可另外「發表動態」將足跡轉為可分享狀態（可見性分級見待確認事項）

*邊界情況／失敗處理*
- 無定位權限：足跡仍可生成，地點標示「位置未知」或手動選擇場館
- 離線：先本地暫存，恢復網路後同步，不遺失

*驗收標準（Acceptance Criteria）*
- AC1：AI 推薦成功後自動生成足跡，無需手動操作
- AC2：足跡可編輯（心情／配圖）與刪除
- AC3：預設可見性為僅自己
- AC4：無定位／離線時仍可正常生成足跡，有明確降級路徑

**UR 3.2　個人足跡時間軸與地圖檢視**

作為使用者，我希望能用時間軸或地圖兩種方式瀏覽我自己的足跡記錄，這樣即使還沒有朋友一起用，單人使用也有價值。

*範圍*
- 個人視角的時間軸列表與地圖標記兩種檢視模式
- 基礎統計（本月喝了什麼類型、頻次分佈），為未來口味畫像累積基礎資料

*驗收標準（Acceptance Criteria）*
- AC1：可切換時間軸／地圖兩種檢視
- AC2：有基礎統計呈現（品類分佈、頻次）
- AC3：未登入的匿名足跡本地保存不遺失，登入後可同步

**UR 3.3　公開地圖與乾杯**

作為使用者，我希望在公開地圖上看到其他使用者公開的足跡，可以點擊頭像對他發起乾杯，這樣可以感受到同城共飲的氛圍、發現新場子。

*範圍*
- 公開地圖僅顯示使用者主動設為「公開／發表動態」的足跡
- 點擊他人頭像可查看該筆公開足跡內容，並可發起「乾杯」
- 乾杯有明確儀式回饋（動畫／震動／音效），尊重 `prefers-reduced-motion`
- 可按酒類過濾；點擊熱力點可見場館資訊（接香港本地酒吧數據，呼應願景中的流量入口）

*隱私與安全（硬約束）*
- 公開地圖定位一律模糊到街區／場館級，不暴露精確座標
- 陌生人之間不可直接私訊，只能發乾杯邀請
- 乾杯邀請需有頻率限制（例如對陌生人的乾杯邀請有每日上限），防止騷擾式濫發
- 提供封鎖與檢舉機制，封鎖後對方無法再對你發起任何互動

*驗收標準（Acceptance Criteria）*
- AC1：公開地圖僅顯示使用者主動公開的足跡，不洩漏未公開足跡
- AC2：乾杯有明確儀式回饋，尊重 reduced-motion 設定
- AC3：陌生人乾杯邀請有頻率限制
- AC4：封鎖／檢舉機制可正常運作

**UR 3.4　乾杯互相回應＋建立好友關係**

作為使用者，我希望當對方回應我的乾杯邀請後，我們就成為好友，可以互相看到更多足跡內容。

*範圍*
- 乾杯邀請可被接受或忽略／拒絕；雙方互相回應後自動建立好友關係
- 成為好友後，彼此可見更多層級的足跡內容（相較陌生人只能看公開足跡）

*不在範圍內*
- 好友間即時聊天功能（延後至 v2，見待確認事項；範圍涉及訊息基礎設施、通知、內容審核、封鎖後訊息處理，範圍不小，先不納入 v1）

*驗收標準（Acceptance Criteria）*
- AC1：雙方互相回應乾杯後正確建立好友關係
- AC2：好友可見的足跡層級正確區隔於陌生人可見範圍
- AC3：v1 不含聊天入口

**UR 3.5　好友列表管理**

作為使用者，我希望能看到我的好友列表，並且可以刪除好友。

*範圍*
- 好友列表檢視
- 可刪除好友關係，刪除後對方降回陌生人的可見層級

*驗收標準（Acceptance Criteria）*
- AC1：好友列表可正常瀏覽
- AC2：刪除好友後，雙方可見層級正確降回陌生人層級

*待確認事項（EPIC 3.0 彙總，待 PM 整理）*
