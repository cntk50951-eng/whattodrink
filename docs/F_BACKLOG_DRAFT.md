## EPIC F — 组局（Group Gathering）总览

**愿景**：以“每人带一支酒的品酒会”为原型的主题化小聚引擎，承载 B+C 双动因（主题开放 + 熟人基座），初期纯信息撮合 + 免责声明 + 公开场所引导，后期叠加认证合作场地。

**MVP 闭环**：发布 → 发现（地图+列表）→ 申请 → 审批 → 行前提醒 → 签到 → 互评

**与主线关系**：复用 EPIC 1.0 地图、3.0 社交（好友/乾杯/在线）、4.0 内容（检举/评价），不引入新 IM，不做电商。

---

### UR F.1 — 组局发布（最小可用） [优先级 P0]

**作为** 想认识新朋友的 Host，我想用 1 分钟发布一个组局（标题/主题/时间/人数/地点/带的酒/简介），以便他人能在地图上发现我。

**范围**：
- 发布页 `/v2/gatherings/new`：标题≤30、主题6选1（BYOB/烤肉/CityWalk/酒吧探店/酒桌游戏/无酒精友好）、时间（未来2h–14天）、人数2–8、地点文本+地图选点（模糊坐标）、BYOB 必填带的酒、简介≤200、可见性 public/friends、审批模式 manual/auto、费用说明（AA 文本）、免责勾选双处。
- 校验：禁止住宅/酒店关键词、时长≤3h、年龄≥18、每周限发2局。
- 数据：`gatherings` 主表（见设计 doc §6）。

**AC**：
- AC1 发布成功后出现在发现列表/地图，状态 open。
- AC2 非法输入（私宅关键词/未成年/未勾免责）阻断并提示。
- AC3 三语、reduced-motion、v2-only。

---

### UR F.2 — 组局发现（地图+列表） [P0]

**作为** 想参加组局的人，我想在地图和列表中发现附近的组局并筛选，以便快速找到感兴趣的局。

**范围**：
- 地图“组局”图层开关（独立于打卡层，pin 用“人+酒杯”图标，与打卡 pin 区分）。
- 列表 Tab：卡片含主题徽章、时间、地点区（如“中环”）、人数进度、好友加成（“有2位好友参与”）、认证场地蓝V。
- 筛选：距离/时间/主题/仅看好友参与的局；分页。
- 详情页只读版（标题/主题/时间/地点模糊/人数/Host 信息/简介/带的酒清单/免责提示）。

**AC**：
- AC1 地图与列表数据一致，切换图层不影响打卡层。
- AC2 好友参与的局有加成标识。
- AC3 筛选与分页可用，空态友好。

### UR F.3 — 申请与审批（含通知） [P0]

**作为** 申请人/Host，我想申请加入或审批申请，以便完成撮合。

**范围**：
- 申请人：详情页“申请加入”→ 附言 + 带的酒 →  pending；可取消申请。
- Host：申请列表（申请人头像/性别/履约率/带的酒/附言）→ 通过/拒绝；满员自动 full。
- 通知：申请、通过/拒绝、满员、取消（站内 Bell，复用现有 realtime 基建）。
- 可见性 friends 生效（仅好友可见的局对非好友隐藏）。

**AC**：
- AC1 申请→ pending → Host 操作后状态流转正确并通知双方。
- AC2 非 Host 不可见管理入口；陌生人不可私信绕过申请。
- AC3 friends 可见性按 `friendships` 生效。

### UR F.4 — 行前提醒与签到 [P1]

**作为** 已确认的参与者，我想在到点前收到提醒并签到，以便确认履约。

**范围**：
- 行前提醒：开始前 24h/2h 站内提醒。
- 签到：到点前30min开放，Host 展示 30s 刷新二维码，参与者扫码或 Host 手动勾选；签到后精确地点对参与者可见。
- 签到后自动生成一条“组局足迹”可选（复用 checkins，待定）。

**AC**：
- AC1 二维码定时刷新，截屏复用无效（MVP 可先静态码）。
- AC2 签到率计入信用分。

---

### UR F.5 — 互评与信用 [P1]

**作为** 参与过组局的人，我想评价同局的人并看到 Host 的历史评分，以便建立信任。

**范围**：
- 签到后 48h 内可评：1–5星 + 标签（准时/友善/分享欲强）+ 可选文字；匿名聚合。
- Host 与参与者互评，履约率 = 签到/确认数，影响后续推荐权重与发现排序。
- 评价区在详情页展示聚合分与标签云。

**AC**：
- AC1 每人每局对每人限评一次，重复提交拦截。
- AC2 未签到者不可评。

### UR F.6 — 认证合作场地（Stage 2） [P2]

**作为** 运营，我想维护一个持牌合作场地库并让组局关联场地获蓝V加权，以便提升安全与体验。

**范围**：
- venues 表（名称/地址/坐标/持牌号/verified/badge）。
- 发布时可选“关联认证场地”，关联后卡片蓝V、列表加权、详情展示场地权益（如折扣）。
- 管理后台（MVP 可用 SQL + 静态列表代替）。

**AC**：
- AC1 关联场地后详情正确展示，未关联不影响发布。
- AC2 非认证地点仍可发布，但无加权。

## AI 内容审核专项（新增，按你要求优先列入）

> 目标：F 线所有用户生成内容（UGC）在入库/展示前过 AI 审核，拦截私宅/酒店/未成年/骚扰/广告/过量饮酒煽动等，辅以人工复审，不做先发后审的裸奔。

### UR F.AI.1 — 文本智能审核管线（标题/简介/附言/带的酒） [P0，F.1 前置]

**作为** 平台，我想在组局标题、简介、带的酒、申请附言提交时自动过 AI 文本审核，以便拦截违规内容再入库。

**范围**：
- 接入文本审核模型（建议：OpenAI moderation / 自托管敏感词+LLM 双层；MVP 可先用 `lib/moderation.ts` 纯函数封装，便于切换供应商）。
- 审核维度：① 私宅/酒店/住宅邀约 ② 未成年/拼酒/酗酒煽动 ③ 骚扰/歧视/色情 ④ 广告/导流/联系方式 ⑤ 违法/危险行为。
- 策略：`block`（硬拦截，返回具体原因，引导改为公开场所） / `review`（进人工待审，暂不上架） / `pass`。
- 前端：提交时 loading + 失败原因回显（例：“地点含私宅关键词，请改为公开餐饮场所”）；后端：入库前必过审，绕过直接调 API 亦拦截。
- 数据：`gathering_moderation_logs`（gathering_id, field, verdict, reason, model_version, created_at）。

**AC**：
- AC1 命中私宅/拼酒等硬规则 → 提交阻断，提示可操作。
- AC2 疑似违规进 review 队列，不在发现页展示，Host 可见“审核中”。
- AC3 三语错误提示；审核日志可追溯。
- AC4 单测：各维度命中/误伤用例 ≥15 例。

**依赖**：F.1 联调；模型 key 存 `.env`，不硬编码。

---

### UR F.AI.2 — 地点与图片智能审核 [P1]

**作为** 平台，我想对组局地点文本+坐标及可选的场地照片做 AI 审核，以便识别私宅/酒店房间与不适宜图片。

**范围**：
- 地点：文本+坐标反查（Nominatim）→ 若解析为 residential/hotel 且无持牌信息 → 触发 review；坐标落在纯住宅区（OSM landuse=residential 且无 POI）→ 提示“建议改至持牌餐饮场所”。
- 图片（若 F.1 允许上传场地照/酒照，MVP 可先不上图片，此 UR 预留）：NSFW/未成年/隐私泄露检测；复用墙的审核能力。
- 复审工作台：最简为 Supabase SQL + 管理页列表（待审→ 通过/下架），不做复杂后台。

**AC**：
- AC1 私宅坐标提交 → 拦截或转人工，提示明确。
- AC2 图片 NSFW 命中 → 阻断上传。
- AC3 审核结果与 F.AI.1 同日志表聚合。

---

### UR F.AI.3 — 审核运营与风控看板（轻量） [P1]

**作为** 运营，我想看到待审队列、拦截率、误伤申诉，以便持续调优模型与规则。

**范围**：
- 看板（MVP 可为 `/v2/admin/moderation` 仅管理员可见，或直接用 Supabase Dashboard + 视图）：待审列表（标题/地点/原因/时间）、一键通过/下架、申诉入口（Host 可申诉一次）。
- 指标：日拦截数、review 占比、申诉成功率、复审时效。
- 模型可配置：阈值、关键词库热更新（存 `moderation_rules` 表）。

**AC**：
- AC1 待审局不在公开发现页，仅 Host 与管理员可见。
- AC2 申诉后 24h 内复审闭环。
- AC3 规则热更新无需发版。

---

### UR F.AI.4 — 反刷与行为风控（AI 辅助） [P2]

**作为** 平台，我想对刷局/幽灵局/频繁取消等行为做 AI 辅助识别，以便保护真实用户。

**范围**：
- 规则 + 轻量模型：同一用户周发2局上限、申请取消率、签缺率、文本相似度（复制粘贴刷局）→ 命中则限流或进 review。
- 与 F.5 信用分联动：低信用 Host 的局在发现页降权。

**AC**：
- AC1 刷局文本相似度 >0.9 → 自动 review。
- AC2 周发超限 → 前端阻断。
