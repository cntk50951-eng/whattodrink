# 2026-10-11 — 加好友 500（42501 RLS）：写路径依赖 insert 策略，且残留行无处理

## 情境

- iOS 陌生人聊天点「加好友」→「好友邀請失敗」。Vercel 日志：`insert error: code=42501 … violates row-level security policy for table "friendships"`。

## 问题

1. 日志直接否定了 iOS 的猜测（23505 唯一键）：是 RLS 拒写。
2. 仓库里 0010 的 insert 策略（`auth.uid()=user_id AND user_id<>friend_id AND status='pending'`）对当前请求应该成立，但生产上实际拒了。
3. 另有真实缺口：`CHECK` 允许 `blocked`，本方向若残留此状态的行，decide 不命中任何分支 → insert 撞唯一键 → 500。
4. 错误文案不带错误码，iOS 无法自查。

## 原因（待 SQL 证实）

- 生产 `friendships` 的 insert 策略很可能与仓库不一致（Dashboard 手改或迁移未全跑），或 `auth.uid()` 与 `user_id` 在该请求里不一致。
- 无论哪种，服务端写路径不该依赖一条会漂移的策略：userId 已由 token 验证，查询全部限定在「我和对方」。

## 修正

1. `POST /friends` 的 friendships 读、翻转、插入全部改 service（与 DELETE／accept 同口径）。
2. 本方向残留非 pending/accepted 行：update 为新请求（不 insert）。
3. 失败文案 `好友邀請失敗（db <code>）`，iOS 可直接显示。
4. 未动：insert 的 23505 重试一次保留（并发竞态）；reverse 翻转与 chat_mutes 清理语义不变。

- 判例：服务端已鉴权的写，不要让 RLS 当第二道门去拒合法请求——拒了只会以 42501 出现，排查成本高。
- 判例：状态机的分支必须穷举 CHECK 允许的所有值（或在残留处显式处理），否则未覆盖的状态会落到 insert。
- 未做：生产策略与仓库是否一致需用户跑 `pg_policies` 核对（见 iOS 文档第八节回复）。
