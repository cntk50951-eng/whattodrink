# UR Status — 需求狀態標記規範

每個 UR 標題行尾必須帶且僅帶一個狀態 tag，格式與 backlog 現有寫法一致：

| Tag | 含義 | 誰可以寫 |
|---|---|---|
| `[]` | Pending：從未開始，或開始了但沒有任何進展可言 | 任務開始時補上 |
| `[WIP]` | 進行中：已動手，但用戶**沒有確認真正完成**（含已合併、已上線但未驗收） | 開工時標上 |
| `[x]` | 完成：用戶**明確確認**該 UR 完成（「OK／可以／完成／過」等針對該 UR 的表態） | 只在確認後打勾 |

## 硬規則

1. **開工前檢查（workflow Step 1 的一部分）**：讀 backlog 時，凡本次要碰的 UR
   沒有 tag，一律先補 `[]` 再往下走。不許帶著無狀態 UR 開工。
2. **開工即 WIP**：第一個實作動作（寫碼／改文檔內容，不含提問和閱讀）之前，
   把該 UR 置 `[WIP]`。
3. **完成確認才能勾**：以下**都不等於完成**，不許擅自打勾——
   - 測試全綠／tsc 全過／lint 全過（那只是門檻）
   - 已 commit／已 push／已合併到 main（那只是交付動作）
   - 用戶說「繼續下一個」（那只是轉場，舊 UR 若無明確驗收詞仍是 WIP）
   - 你自己覺得做完了（你的感覺不算數）
4. **用戶的完成確認必須是針對該 UR 的**：籠統的「不錯」「好」若指向單個細節
   修改，不算 UR 完成；拿不準就問一句再勾，問比錯便宜。
5. **回寫時機**：狀態變化當下就改 backlog，不要攢到 commit 時；
   状态本身是文档改动，随相关 commit 一起提交即可，不必单独 commit。

## 範例

```md
**UR 1.1　首頁動態地圖重構（Web POC）** [x]
**UR 1.2　首頁地圖小屏交互重做（Web POC）** [WIP]
**UR 1.3　手機地圖高度與面板體驗優化** []
```
